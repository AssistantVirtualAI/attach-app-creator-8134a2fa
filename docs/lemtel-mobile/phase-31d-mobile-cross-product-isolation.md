# Lemtel — phase 31D : isoler les appels mobiles Planiprêt et le carnet hérité

**État au 4 octobre 2026 : code non distribué.** La phase 31C a trouvé trois appels `pp-*` dans le mobile Lemtel. Sur un **nouvel émetteur Auth/API auto-hébergé**, la phase 31D bloque ces appels ainsi que le consentement et le cache Contacts de l’ancien produit. Les builds toujours dirigés vers l’origine historique gardent leurs fonctions antérieures. Aucun serveur, DNS, PBX, carnet réel ni donnée utilisateur n’a été modifié par ces tests.

| Fonction historique | Nouveau build auto-hébergé | Build historique |
| --- | --- | --- |
| `pp-caller-lookup` | Affiche le numéro brut normalisé; ne transmet pas le numéro à Planiprêt. L’enrichissement CRM manque encore. | Appel et cache historique inchangés. |
| `pp-contacts-upsert` et lecture du carnet | **Aucune lecture du carnet, permission native, accès au cache/consentement legacy ou transmission serveur.** Le démarrage, la composition, le répertoire et le bouton de synchronisation se ferment à la source. L’écran indique la fonction indisponible; le répertoire d’extensions et les contacts **saisis manuellement** ne pourront fonctionner qu’une fois leurs API Lemtel autonomes déployées et vérifiées. | Consentement et synchronisation historiques inchangés. |
| `pp-wss-fallback-log` | Diagnostic SIP local, sans téléverser les URLs WSS ni les résultats vers Planiprêt. | Journal historique inchangé. |

La description Contacts native iOS est rendue exacte pour les deux modes : aucune autorisation Contacts n’est demandée dans le build dirigé vers le nouvel émetteur, **y compris au premier login iOS**, où un chemin automatique supplémentaire a été fermé. Sur l’origine historique, ce chemin iOS attend désormais le consentement explicite déjà exigé par la feuille. Le raccourci Contacts du numéroteur et le bouton « supprimer mes contacts du serveur » historique sont masqués dans le nouveau mode, sans supprimer le clavier ou l’appel SIP. **Il ne s’agit pas d’une fonction Contacts locale réimplémentée** : elle exige un consentement neuf, isolé par compte et origine, ainsi qu’un cache distinct avant d’être rétablie. Même une permission OS déjà accordée ou un consentement/cache Planiprêt préexistants ne sont pas repris. Cette limitation est volontaire et visible, non présentée comme une synchronisation réussie.

**Validation locale :** TypeScript, suite Vitest mobile complète (**240 tests réussis, 3 ignorés, 43 fichiers passés**) et build Vite; tests spécifiques de refus réseau, de cache/consentement historiques préremplis, d’accès natif déjà autorisé, de premier login iOS, du répertoire et du numéroteur, plus continuité du mode historique. Le plist iOS est valide. Aucun appel à FusionPBX, Hostinger ou DigitalOcean. La suite concerne le JavaScript mobile : elle ne remplace ni une recette iOS/Android native ni un essai d’appel réel.

**Reste à faire :** revoir les dépendances indirectes de 31C; concevoir les fonctions `lemtel-*` avec Auth/RLS propres et consentement; créer et vérifier une baseline DB/Storage/Realtime indépendante sans migration Planiprêt; préparer la pile HTTPS Hostinger **après admission opérationnelle**, puis son secours DigitalOcean avec sauvegarde restaurable et bascule testée; recetter les appels avec Kenny/Phil et signer les builds mobiles. La politique d’admission v1 est toujours `denied`. Ni cette PR ni le pointage DNS ne signifient que l’application fonctionne sur Hostinger.
